# fin_edu 학급 신용평가 모델

초등학교 교실에서 운영하는 **모의 경제 사회**의 신용평가 엔진이다.
학생들은 실제 돈 대신 학급 화폐로 급여를 받고, 세금을 내고, 저축하고, 대출을 갞는다.
이 저장소는 그렇게 쌓인 거래 기록과 생활 기록을 읽어
**학생별 신용점수(350~1000점)와 신용등급(1~10등급), 그리고 그 이유**를 만들어 낸다.

실제 신용평가사가 쓰는 방식(WoE 구간화 + 로지스틱 회귀 스코어카드, PDO 점수 스케일링)을
그대로 따르되, 교실에서 쓸 수 있도록 **모든 점수를 항목별 배점으로 분해해 설명**한다.

```
서민준 · 4학년 1반                      516점   10등급(위험)

점수를 깎은 이유
  남은 대출 잔액          -137점   빗을 조금씩 줄여 나가 보세요.
  지출 대비 여유 자금(주)  -21점   1~2주치 생활비는 남겨 두세요.
  최근 8주 지출            -21점   지출을 기록하고 새는 돈을 찾아보세요.
```

여기서 점수 옆의 숫자는 비유가 아니라 **실제 배점 차이**다.
신용점수는 피처별 배점의 합으로 정의되어 있고, 학급 중앙값과의 차이를 그대로 보여 준다.

## 2. 빠르게 실행하기

```bash
git clone <this repo> && cd ai
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env          # DB 접속 정보 확인/수정

export PYTHONPATH=src
python -m fin_edu_credit.cli all       # migrate -> seed -> train -> score
python -m fin_edu_credit.cli serve     # http://localhost:8899
```

명령별로 나눔 실행할 수도 있다.

| 명령 | 하는 일 |
| --- | --- |
| `migrate` | 잘못된 제약 정리 + `credit_score`/`credit_model_run` 생성 |
| `seed` | 더미 모의 경제 생성 후 DB 적재 (`--dry-run` 으로 통계만 확인 가능) |
| `train` | 스코어카드 학습, `artifacts/credit_model.joblib` 과 `reports/` 저장 |
| `score` | 전교생 점수 산출 후 `credit_score` 적재 (`--write-report` 로 `ai_report` 까지) |
| `report` | 최근 학습의 정보값(IV)·검증 지표·구간별 배점표 출력 |
| `serve` | 조회 API 와 대시보드 실행 |

## 3. 먼저 고쳐야 했던 것: 스키마 제약

작업을 시작할 때 `fin_edu` 스키마에는 복사-붙여넣기로 들어간 것으로 보이는 UNIQUE 제약이 있었다.

```sql
-- transaction 테이블
UNIQUE KEY `member_id_UNIQUE` (`account_id`)   -- 계좌 하나에 거래 1건만 가능
-- payroll 테이블
UNIQUE KEY `member_id_UNIQUE` (`member_id`)    -- 학생 한 명에게 급여 1회만 가능
```

이름은 `member_id_UNIQUE` 인데 실제로는 `account_id` 에 걸려 있다.
이 상태로는 거래 원장 자체가 성립하지 않아 신용평가를 할 수 없으므로,
`sql/001_fix_schema_constraints.sql` 에서 제거했다.
두 인덱스가 각각 외래키를 떠받치고 있어서 **대체 인덱스를 먼저 만든 뒤** 제거해야 한다.

또한 요청에 있던 `balance` 테이블은 별도로 존재하지 않고 `account.balance` 컬럼이다.
잔액 관련 피처는 이 컬럼과 거래 누적합에서 만들었다.

## 4. 더미 데이터: 무엇을 시뮬레이션했나

학생마다 서로 다른 행동 패턴이 나오도록, 두 개의 잠재 성향을 부여했다.

* **성실성(theta)** — 출석률·숙제완료율·도서 반납·상환 의지를 함께 끌어올린다.
* **충동성(impulse)** — 간식·뽑기 쪽으로 소비를 몰고 잔액을 말린다.

이 성향은 **DB 에 저장하지 않는다.** 모델은 성향을 볼 수 없고,
성향이 만들어 낸 행동의 흔적만 보고 연체를 예측해야 한다.

급여는 **한 달에 한 번** 줌다. 한 달을 달력 대신 4주로 고정한다.
관측 윈도우(8주)에 급여일이 2번 들어갈 때와 3번 들어갈 때가 생기면,
행동과 무관하게 소득 피처가 50%씩 출렁이기 때문이다.

한 달의 리듬은 이렇게 흘러간다.

```
1주차  월급 지급, 적금 자동이체, 예금 이자
       (결석한 주만큼 그달 월급에서 깎인다)
2주차  세금 납부        (소득세 / 건강 보험료 / 자리 임대료 / 학급 기금)
3주차  대출 상환
4주차  의무 지출 없음
매주   재량 소비        (남은 잔액에 비례, 충동성이 높을수록 크게)
       예상 못 한 지출  (준비물, 친구 선물 등)
```

납부일을 월 후반에 두는 것이 핵심이다. 월급 바로 다음 주에 걷으면
통장이 아직 두둡해서 아무도 밀리지 않고, 그러면 대출을 쓠 학생만
위험해 보이는 모델이 된다. 월급을 받자마자 다 써 버리면 2주차 세금과
3주차 상환에서 돈이 모자란다. '목돈이 들어왔을 때 나눔 쓰는 법'이
이 모의 경제의 학습 지점이다.

잔액이 모자라면 **적금을 깨서** 메우고, 그래도 모자라면 납부를 못 해
`대출 상환 연체료` 또는 `세금 체납 가산금` 이 붙는다. 이 연체 거래가 곧 정답 라벨이다.
돈이 있어도 깜빵할 수 있도록, 관측되지 않는 달별 성실성 충격을 넣었다.
모델이 잔액만으로 연체를 거의 확정하지 못하게 하기 위해서다.

생성 규모(기본값)는 다음과 같다.

| 테이블 | 건수 |
| --- | --- |
| `member` | 312 (학생 300 + 담임 12) |
| `account` | 651 (입출금 312 / 적금 · 대출 339) |
| `transaction` | 약 62,000 |
| `payroll` | 약 2,600 |

연체 이벤트는 4주 성과 윈도우 기준 학생의 약 18~23% 에서 발생한다.
실제 신용평가 데이터의 부실률보다는 높지만, 학습이 가능한 수준의 불균형이다.

## 5. 모델 설계

### 5.1 관측 윈도우와 성과 윈도우

```
        ← 관측 8주 →  기준일  ← 성과 4주 →
        ─────────────├─────────────
         피처를 만든다  │  연체하면 bad(1)
```

기준일을 2주 간격으로 옮기며 12개 스냅숏을 만들어 **3,575행** 의 패널 데이터를 얻는다.
같은 학생이 여러 스냅숏에 등장하므로, 학습/검증 분할과 교차검증은 **모두 학생 단위**(`GroupShuffleSplit`,
`StratifiedGroupKFold`)로 한다. 행 단위로 자르면 같은 학생이 양쪽에 들어가 성능이 부풀려진다.

### 5.2 입력 피처 (29개)

| 분류 | 피처 |
| --- | --- |
| 생활 기록 | `cs_attendance` 출석률, `cs_homework` 숙제완료율, `cs_overdue` 도서 연체 |
| 연체/상환 | 최근 연체 횟수·연체료, 마지막 연체 이후 경과일, 대출 상환 이행률, 세금 납부 이행률, 벌금 횟수 |
| 현금흐름 | 수입, 지출, 순현금흐름, 수입 대비 소비 비율, 급여 수령 규칙성 |
| 저축/자산 | 저축률, 적금 납입액, 적금 잔액, 입출금 잔액, 총 자산, 적금 가입 여부 |
| 부채/유동성 | 남은 대출 잔액, 월 소득 대비 부채, 대출 이용 여부, 여유 자금(주), 최저 잔액, 잔액 부족 비율, 잔액 변동성 |
| 소비 습관 | 충동 소비 비중, 계좌 개설 경과일 |

시점 잔액은 `account.balance` 를 그대로 쓰지 않고 **거래 누적합으로 복원**한다.
그래야 과거 어느 기준일에서도 그 시점의 잔액을 정확히 알 수 있다
(테스트 `test_account_balance_equals_transaction_sum` 이 이 전제를 검증한다).

### 5.3 왜 WoE 구간화인가

원시 피처를 그대로 로지스틱 회귀에 넣으면 서로 상관된 피처끼리 계수 부호가 뒤집힌다.
실제로 첫 시도에서는 이런 결과가 나왔다.

```
savings_deposit_8w  -0.589   (저축할수록 안전)
savings_rate        +0.469   (저축률이 높을수록 위험)   ← 같은 저축인데 부호가 반대
late_events_8w      -0.340   (연체가 많을수록 안전)     ← 상식과 반대
```

이런 모델로는 "적금을 많이 해서 점수가 깎였어요" 같은 설명이 나온다. 교실에서는 쓸 수 없다.

그래서 각 피처를 **도메인 방향에 맞춰 단조가 되도록** 구간화한다.
출석률은 높을수록 WoE(안전도)가 커지도록, 부채는 클수록 WoE 가 작아지도록
인접 구간을 병합해 나간다. 방향이 끝내 맞지 않는 피처는 구간이 하나로 합쳐져
정보값(IV)이 0 이 되고 자동으로 탈락한다. **가정한 방향과 반대로 움직이는 피처는 아예 쓰지 않는다.**

### 5.4 왜 부호 제약 회귀인가

WoE 를 써도 상관된 피처가 남아 있으면 계수 부호는 여전히 뒤집힐 수 있다.
흔한 대처는 부호가 틀린 피처를 하나씩 빼며 재적합하는 것인데,
그러면 출석률·저축처럼 **교육적으로 꼭 보여 줘야 하는 항목이 연쇄적으로 탈락**한다.
실제로 그 방식에서는 부호 위반을 이유로 8개 피처가 연달아 빠졌다.

그래서 `scipy.optimize` 의 L-BFGS-B 로 **계수 상한을 0 으로 두고** 최적화한다
(`src/fin_edu_credit/linear.py`). 기여할 것이 없는 피처는 탈락하는 대신 계수가 0 으로 수렴한다.

피처 선별 순서는 다음과 같다.

```
29개 피처
  → IV < 0.02 제외              (예측력 없음)
  → WoE 상관 0.80 초과 제외      (정보값이 낮은 쪽)
  → 부호 제약 적합 후 계수 0 제외
  → 13개 채택
```

### 5.5 점수와 등급

로지스틱 회귀가 내놓는 값은 '앞으로 4주 안에 연체할 확률(PD)'이다.
이를 표준 스코어카드 방식으로 점수로 바꾼다.

```
score  = offset + factor · ln(odds),   odds = (1 − PD) / PD
factor = PDO / ln 2
offset = 기준점수 − factor · ln(기준 odds)
```

기준점수 650점, 기준 odds 3:1, PDO 40점을 쓰다.
**정상:연체 odds 가 2배 좋아질 때마다 40점씩 오른다**는 뜻이다.
월급 주기로 바꾸 뒤 PDO 60이면 점수가 1000점에 몰려, 학급 분포에 맞게 줄였다.

이 정의 덕분에 점수를 피처별 배점으로 정확히 쪽갤 수 있다.

```
배점(피처 f, 구간 b) = (offset − factor·b₀)/n − factor · β_f · WoE_b
score = Σ 배점
```

테스트 `test_points_sum_equals_score` 가 **배점의 합이 PD 변환 점수와 정확히 일치**함을 확인한다.
사유코드는 근사치가 아니라 정확한 분해다.

## 6. 성능

학생 단위로 나눈 검증셋(75명 · 892행) 기준이다.

| 지표 | 값 | 의미 |
| --- | --- |
| AUC | **0.734** | 연체할 학생과 아닌 학생을 무작위로 뽑았을 때 순위를 맞출 확률 |
| Gini | 0.468 | 2·AUC − 1 |
| KS | 0.441 | 정상/연체 누적분포의 최대 격차 |
| Brier | 0.124 | 예측 확률의 보정 품질(낮을수록 좋음) |
| 부실률 | 17.8% | 검증셋의 실제 연체 발생 비율 |

비교 기준으로 원시 피처를 그대로 쓰는 그래디언트 부스팅도 함께 학습했다.

| 모델 | 교차검증 AUC | 검증 AUC |
| --- | --- |
| **WoE 스코어카드 (채택)** | **0.736** | **0.734** |
| HistGradientBoosting (비교) | 0.729 | 0.701 |

해석 가능성을 얻으려고 성능을 희생한 것이 아니라, 이 데이터에서는 스코어카드가 더 낫다.
표본이 작고(학생 300명) 신호가 단조로울 때 구간화 + 선형 결합이 과적합에 강하기 때문이다.

점수 구간별 실제 연체율은 아래처럼 단조롭게 떨어진다.

| 점수 구간 | 인원 | 연체율 |
| --- | --- |
| 467 ~ 549 | 91 | 59.3% |
| 549 ~ 587 | 88 | 35.2% |
| 587 ~ 675 | 92 | 20.7% |
| 675 ~ 717 | 179 | 6.7% |
| 717 ~ 820 | 442 | 9.7% |

| 도서 연체 횟수 | 0.060 | 약함 | O |

빗과 현금흐름이 가장 강한 신호이고, 생활 습관 지표는 그다음이다.
생활 습관은 IV 는 낮지만 학생이 **직접 바꿀 수 있는 항목**이라 모두 남겨 두었다.

---

## 7. 두 가지 점수를 함께 내는 이유

모델 점수만으로는 "왜 내가 5등급이야?" 에 칠판으로 답하기 어렵다.
그래서 선생님이 설명할 수 있는 **규칙기반 점수**를 나란히 내다.

| 항목 | 비중 |
| --- | --- |
| 약속한 납부 지키기 | 25% |
| 출석 | 15% |
| 숙제 | 15% |
| 저축 | 13% |
| 소비 관리 | 10% |
| 여유 자금 | 8% |
| 도서 반납 | 7% |
| 빗 관리 | 7% |

`credit_score` 테이블에 `score`(모델)와 `rule_score`(규칙)가 함께 저장된다.
두 점수는 대체로 비슷하게 움직이며, 크게 벌어지는 학생은 개별 상담 대상으로 삼을 수 있다.

## 8. 산출물

### `credit_score`

| 컬럼 | 설명 |
| --- | --- |
| `score`, `grade`, `grade_label` | 모델 점수와 1~10 등급 |
| `pd` | 향후 4주 연체 예측 확률 |
| `rule_score`, `rule_grade` | 규칙기반 점수 |
| `reason_json` | 감점/가점 사유코드, 요약문, 항목별 달성도 |
| `feature_json` | 평가에 사용한 입력 피처 스냅숏 |

`(member_id, evaluated_at, model_version)` 이 유일키라서 기준일별 이력이 쌓인다.

### `credit_model_run`

학습할 때마다 모델 버전·알고리즘·AUC/KS/Gini/Brier 와 전체 지표 JSON 을 남긴다.

### `ai_report`

`score --write-report` 를 쓰면 학생별 요약문이 기존 `ai_report` 테이블에도 반영된다.

```
서민준 학생의 학급 신용점수는 516점, 10등급(위험)입니다.
점수를 가장 많이 깎은 항목은 남은 대출 잔액(-137점)입니다.
빗을 조금씩 줄여 나가 보세요.
그 밖에 지출 대비 여유 자금(주), 최근 8주 지출 도 살펴보면 좋아요.
```

* 같은 피처 안에서 안전한 구간이 항상 더 높은 배점을 받는가

## 12. 한계

* **더미 데이터로 학습한 모델이다.** 실제 학급 데이터가 쌓이면 다시 학습해야 한다.
  성능 지표도 시뮬레이션 세계 안에서의 값이다.
* 연체 라벨은 `대출 상환 연체료` / `세금 체납 가산금` 거래로 정의했다.
  실제 운영에서 연체를 다르게 기록한다면 `domain.LATE_EVENT_DESCRIPTIONS` 를 맞춰야 한다.
* 4주 성과 윈도우는 학기 길이를 고려한 값이다. 운영 주기가 다르면
  `ModelConfig.performance_weeks` 를 조정하고 재학습해야 한다.
* 학생 300명 규모라 IV 가 낮은 생활 습관 지표의 계수는 표본에 따라 흔들린다.
  등급 구간표(`GRADE_TABLE`)도 현재 점수 분포에 맞춰 놓은 값이므로,
  모집단이 바뀌면 다시 맞춰야 한다.
